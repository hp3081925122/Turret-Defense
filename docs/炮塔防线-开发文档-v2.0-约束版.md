## 0. 如何使用本文档

### 0.1 读者

| 角色 | 是谁 | 职责 |
|:---|:---|:---|
| **执行者** | AI 编码代理 | 全权负责全部代码实现。本文件是规格书，不是教程 |
| **所有者** | 人类（编程新手） | 只做两件事：**验收**（按 §9 检查）与**决策**（§11 待定项） |

执行者不需要向所有者解释 Minecraft API 的基础概念。执行者**必须**在每次交付时附上：本次完成了 §9 中的哪几条、哪几条没做到、为什么。

### 0.2 四条不可违反的总原则

**1. 性能是第一考量，优先级高于玩法丰富度与视觉表现。**
任何设计在「性能」与「效果」冲突时，一律让步于性能。
目标场景是 **「工业基地中打尸潮」**（§4.13）—— 大量方块实体 + 200~500 个敌对实体同时进攻，
**不是**空地上摆一座炮塔。凡涉及 tick、实体查询、渲染、网络、粒子的实现，先问一句：
> *1000 个塔头 + 500 个敌人同时存在时，这段代码会怎样？*

**2. 前置模组默认三个，新增必须走准入流程。**
默认硬依赖：Kotlin for Forge、ApricityUI、KubeJS。
要引入任何新的开源库或其他模组，**必须**通过 §1.7 的四条硬性准入条件，并填写 §1.7.2 的论证模板。
> 注意：MC 与 Forge **自带**的库（fastutil / Guava / joml / Mth / slf4j 等）**不算新增依赖**，
> 直接使用即可，且是零成本性能收益的来源（§1.7.3）。

**3. 本文档里的版本号、Maven 坐标、API 签名是硬事实。**
不许升级、不许降级、不许「我记得最新版是」。需要变更时停下来找所有者确认。

**4. 每一期结束时，模组必须能启动、能进游戏、能用。**
不做「半成品架构」，不做「先搭架子以后再填」。

### 1.2 前置一：Kotlin for Forge `[已核实]`

**作用**：提供 Kotlin 语言加载器，让 Forge 能加载 `.kt` 编译出的类。

| 项目 | 值 |
|:---|:---|
| 最新 1.20.1-Forge 版本 | **4.12.0**（2025-12-03，文件名 `kotlinforforge-4.12.0-all.jar`） |
| Maven 仓库 | `https://thedarkcolour.github.io/KotlinForForge/` |
| Maven 坐标 | `thedarkcolour:kotlinforforge:4.12.0` |
| 许可证 | LGPL-2.1 |

**`mods.toml` 中必须声明（这一行写错 = Kotlin 类完全不被加载）：**

```toml
modLoader="kotlinforforge"
loaderVersion="[4.12.0,)"
```

**事件总线**：用 `thedarkcolour.kotlinforforge.forge.MOD_BUS` 取代 `FMLJavaModLoadingContext.get().getModEventBus()`。

**Forge 平台必须追加的构建配置**（KFF 官方 skeleton 的已知要求，用于修正 Kotlin 与 Java 混合编译时的输出目录）：

```groovy
sourceSets.configureEach {
    def dir = layout.buildDirectory.dir("sourcesSets/$name")
    output.setResourcesDir(dir)
    java.destinationDirectory.set(dir)
    kotlin.destinationDirectory.set(dir)
}
```

### 1.3 前置二：ApricityUI（晴雪UI）`[已核实]`

**作用**：用 HTML + CSS + JS 构建全部游戏内 UI。

| 项目 | 值 |
|:---|:---|
| 最新 1.20.1-Forge 版本 | **1.2.7**（2026-10-05，文件 `ApricityUI-forge-1.20.1-1.2.7.jar`，2.68 MB） |
| Maven 仓库 | `https://maven.sighs.cc/repository/maven-public/` |
| Maven 坐标 | `com.sighs:ApricityUI-forge-1.20.1:1.2.7` |
| 许可证 | LGPL-2.1 |
| 官方文档 | `https://doc.sighs.cc/ApricityUI/`（中文） / `.../en/ApricityUI/`（英文） |
| 侧别 | client = **required**，server = **optional** |

**关于侧别的关键判断**：ApricityUI 官方声明服务端可选。但**本项目必须把服务端也设为必需**，因为：

> 我们用的是真物品栏容器路线，而容器的打开入口 `ApricityUI.menu(player, path).bind(...)` **是服务端 API**。
> 若服务端未装 ApricityUI，玩家右键炮塔将什么都打不开。

因此本项目的 `mods.toml` 必须声明 `side="BOTH"`（见 §1.5）。

### 1.4 前置三：KubeJS `[已核实]`

**作用**：为 ApricityUI 页面提供 JavaScript 引擎（Rhino）。**这不是可选项。**

> **关键事实**：ApricityUI 自己的 jar 内**不含任何 JS 引擎**（已通过搜索全部 1034 个 jar 条目确认，`mozilla|rhino|graal|nashorn|javascript` 零匹配）。
> 页面里的 `<script>` 由 **KubeJS 提供的 Rhino** 执行。没有 KubeJS →
> HTML/CSS 照常渲染、Java 侧照常能读写 DOM、**但页面内 `<script>` 完全不执行**。

| 项目 | 值 |
|:---|:---|
| 用途 | 提供 Rhino JS 引擎 + `ApricityUI` 全局对象 + `@KJSBindings` 注册点 |
| 版本 | 选 1.20.1-Forge 分支的最新稳定版；**由执行者在搭建时查询确认后写入 `gradle.properties`**，不要凭记忆填 |
| 侧别 | 客户端必需（页面脚本在客户端执行）；服务端可选 |

**注意**：KubeJS 是本项目里唯一"版本号需要现场查询"的依赖。执行者必须去 Modrinth/CurseForge 查 1.20.1-Forge 的最新版，并把确切版本号写进 `gradle.properties` 与 `mods.toml`。

### 1.5 `mods.toml` 完整规格

```toml
modLoader="kotlinforforge"
loaderVersion="[4.12.0,)"
license="MIT"
issueTrackerURL="https://github.com/<owner>/turretdefense/issues"

[[mods]]
modId="turretdefense"
version="${file.jarVersion}"
displayName="Turret Defense"
authors="<owner>"
description='''
基地核心为唯一枢纽的科技风格防御模组。
炮塔只负责攻击，能量、修复、护盾、索敌、物资补给全部由核心统一管理。
'''

[[dependencies.turretdefense]]
    modId="forge"
    mandatory=true
    versionRange="[47,)"
    ordering="NONE"
    side="BOTH"

[[dependencies.turretdefense]]
    modId="minecraft"
    mandatory=true
    versionRange="[1.20.1,1.21)"
    ordering="NONE"
    side="BOTH"

[[dependencies.turretdefense]]
    modId="kotlinforforge"
    mandatory=true
    versionRange="[4.12.0,)"
    ordering="AFTER"
    side="BOTH"

[[dependencies.turretdefense]]
    modId="apricityui"
    mandatory=true
    versionRange="[1.2.7,)"
    ordering="AFTER"
    side="BOTH"

[[dependencies.turretdefense]]
    modId="kubejs"
    mandatory=true
    versionRange="[2001.6.5,)"

```

> `kubejs` 的 `versionRange` 是**占位示例**。执行者查到实际版本后必须替换成真实值。

### 1.7 依赖准入标准（开源库与其他模组）

> **所有者补充**：可以多多寻找开源库（性能、代码、各种实现），只要**可商用**、**与 MC 合适**、
> **不引入其他额外语言**；若要引用，**必须证明它不会对可维护性造成负担**。**相关设定的其他模组**同样适用。

#### 1.7.1 四条硬性准入条件（必须全部满足）

| # | 条件 | 判定 |
|:--:|:---|:---|
| 1 | **许可证允许商用且允许再分发** | MIT / Apache-2.0 / BSD / LGPL / CC0 通过。**GPL / AGPL / CC-NC / ARR / 无许可证 一律不通过** |
| 2 | **不引入新的编程语言** | 本项目已有语言：Java（Forge API 强制）、Kotlin（主语言）、JavaScript（AUI 页面脚本）。**禁止**引入需要 Rust / C++ / Scala / Groovy / Lua / Python 运行时的依赖 |
| 3 | **不增加可维护性负担**（需书面论证） | 按 §1.7.2 模板填写，结论必须是「负担显著低于自己实现的成本」 |
| 4 | **与 MC 1.20.1 + Forge 47.x 兼容** | 有活跃维护，或已冻结稳定到不需要跟随更新 |

**第 2 条的深层理由**：每多一种语言就多一套构建工具链、多一个调试器、多一处「谁在调用谁」的盲区。
所有者是编程新手，且项目由 AI 全权实现 —— **语言的种类数直接等于出问题时能排查的难度**。

#### 1.7.3 白名单：已内置、零引入成本，**直接用**

**这些库随 Minecraft / Forge 一起提供，不需要在 `build.gradle` 里添加任何依赖。**

> **这本身就是「性能优先」的直接体现** —— 例如 `fastutil` 的 `Long2ObjectOpenHashMap` /
> `ObjectOpenHashSet` 比 Kotlin 的 `HashMap<Long, ...>` 快数倍且无装箱开销，
> 而它是 MC 自带的。用自带库拿性能，是**零成本**的优化。

| 库 | 用途 | 本项目用在哪 |
|:---|:---|:---|
| `it.unimi.dsi.fastutil` | 高性能原生类型集合 | **空间网格 / 快照包含判断 / 候选集**（§4.13.3、§4.13.8） |
| `com.google.common` (Guava) | 通用工具、不可变集合 | 集合构造、工具方法 |
| `org.apache.commons.lang3` | 通用工具 | 字符串、数学 |
| `com.google.gson` | JSON | 调试导出、配置 |
| `org.joml` | 数学库（向量/矩阵） | 需要时使用 |
| `net.minecraft.util.Mth` | MC 数学工具 | `clamp` / `lerp` / 距离 |
| `net.minecraft.world.phys.AABB` / `Vec3` | 几何 | 范围判定、弹道 |
| `org.slf4j` | 日志 | **全部日志输出**（禁止用 `System.out`） |

**ApricityUI 自带、零引入成本，直接用：**

## 2. ApricityUI 能力边界与铁律

> 本章是**踩坑清单**。每一条都来自官方文档或实际 jar 内容，违反任何一条都会产生"看起来应该能跑但实际不工作"的 bug。
> **执行者在写任何 HTML/CSS/JS 之前，必须通读本章。**

### 2.1 它是什么，不是什么

| 是 | 不是 |
|:---|:---|
| 纯 Java 从零实现的 HTML 解析 + CSS 布局 + 渲染引擎 | ❌ 不是内嵌浏览器 |
| 跟随 Web 标准的**子集**，语法尽量贴近标准 | ❌ 不是 Chromium，不捆绑任何浏览器运行时 |
| 支持 HTML / CSS / JS / TTF-OTF 字体 / png-jpg-bmp-gif-webp | ❌ 不支持 video；audio 仅 OGG/WAV（**无 MP3**） |
| JS 由 KubeJS 提供的 **Rhino** 执行 | ❌ 不是现代 JS 引擎，不支持 ES6+ 大部分特性 |

**权威依据**：jar 内 `docs/en/guide/overview.md` 原文 —— *"It is not an embedded browser; AUI implements its own HTML parsing, CSS layout, and rendering."*

### 2.2 四种页面宿主与选型（本项目只用其中两种）

| 宿主 | 创建方式 | 本项目用途 |
|:---|:---|:---|
| `ApricityScreen` | `new ApricityScreen(path)` + `setScreen(...)` | ⛔ **不用**（我们要真物品栏） |
| `ApricityContainerScreen` | `ApricityUI.menu(player, path).bind(...)`（**服务端**） | ✅ **炮塔底座 GUI、核心 GUI** |
| Overlay `Document` | `ApricityUI.createDocument(path)` | ✅ **HUD：炮塔状态提示、能量告警** |
| `WorldWindow` | `ApricityUI.createWorldWindow(path, pos, dist)` | 🔶 第二期考虑（世界内提示牌） |

**「创建 ≠ 显示」**：`createDocument` 只创建 Document（Overlay 会自动渲染）；要 Screen 必须用 `new ApricityScreen` 或 `screen(path)`；要容器必须用 `menu(...).bind(...)`。

### 2.3 资源路径铁律

**所有资源引用一律用逻辑路径**：`screens/turret_base.html`。**绝不**写 `assets/apricityui/apricity/` 前缀，**绝不**写磁盘路径。

物理存放位置（优先级由低到高，同路径后者覆盖前者）：

| 来源 | 位置 | 可写 |
|:---|:---|:---|
| 资源包（打进模组 jar） | `assets/apricityui/apricity/...` | 否 |
| 实例本地目录 | `<实例目录>/apricity/...`（开发环境 `run/apricity/`） | 是 |
| 开发目录 | `src/main/resources/assets/apricityui/apricity/...` | 是 |

**本项目的页面目录结构**（必须严格遵守）：

```text
src/main/resources/assets/apricityui/apricity/
├── global.css                    ← 自动注入每个页面（放本项目全局变量/主题色）
├── global.js                     ← 每个 Document 刷新时执行
├── screens/
│   ├── turret_base.html          ← 炮塔底座 GUI（6 塔头 + 插件 + 弹药 + 缓存）
│   └── base_core.html            ← 基地核心 GUI（能量 + 炮塔列表 + 权限）
├── overlays/
│   └── energy_alert.html         ← 能量不足 HUD 告警
├── styles/
│   ├── theme.css                 ← 本项目配色/面板/按钮
│   └── slots.css                 ← 槽位分区布局
├── scripts/
│   ├── turret_base.js            ← 底座 GUI 交互
│   └── base_core.js              ← 核心 GUI 交互
└── images/
    └── (图标资源)
```

**注意**：路径里的 `apricityui` 是 ApricityUI 模组的命名空间，**不是我们的**。这是 AUI 的固定约定，我们只能服从。
页面之间互相引用 CSS/图片用**相对路径**（相对当前 HTML 文件自己）；以 `/` 开头表示逻辑资源根。

**热重载**：开发期改完 HTML/CSS/JS 后按 `END` 键重载。**F10** 开资源管理器，**F12** 开 DevTools。
⚠️ 这三个按键**默认都未绑定**，必须在 MC 的「控制」设置里手动绑定后才能用。

### 2.4 容器 API 的八条硬限制 `[已核实]`

> 这是本项目 UI 层最容易翻车的地方。八条全部来自官方 `container.md`，逐条遵守。

**① 每个数据源类型，一个菜单只能绑一个。**
`binding.blockEntity(pos).player()` —— 只能有一个 `blockEntity`。我们需要"底座内 6 个塔头"，但物品栏只有一个 `IItemHandler`，**这不是问题**（见第 ③ 条）。但绝不能试图绑定两个 `blockEntity`。

**② 容器 id 是固定的，不能自取名字。**

| 服务端绑定方法 | HTML 里必须用的 id |
|:---|:---|
| `player()` | `player` |
| `saveddata(...)` | `saved_data` |
| `blockEntity(pos)` | `block_entity` |
| `entity(id)` | `entity` |

写错 id → 槽位静默退化为"仅显示"，**不会报错**，极难排查。

**③ `slot-index` 是容器内局部索引。** 全局索引 = 容器 baseIndex + 槽位 slot-index。
底座的 `IItemHandler` 是一个连续数组，我们靠 `slot-index` 把它切成视觉上的不同区域（见 §7.2）。
**同一个容器内两个槽位不得使用同一个 `slot-index`** —— 后扫描到的会覆盖前面的。

**④ 一旦手写一个 `<slot>`，自动生成就完全失效。** 要么全自动，要么全手写。
**并且自动生成的槽位没有稳定 id，无法加物品过滤器。**
→ 结论：**本项目弹药槽必须手写**（否则玩家能把钻石塞进弹药槽），所以底座的整个容器必须全部手写槽位。

**⑤ `repeat="9"` 不会克隆 DOM 槽位**，它只参与容量推断。批量槽位请用空容器 + `size` + 自动生成。
但由于第 ④ 条我们要手写，所以这条用不上 —— **不要试图用 `repeat` 省事**。

**⑥ 玩家离开方块约 8 格，菜单自动关闭。** 底座被移除同样立即关闭。这是框架行为，不要试图绕过。

**⑦ 容器没有标题机制。** `title` 属性不画标题，标题请用普通 `<div>` 自己写。

**⑧ `refresh()` 之后槽位会重新绑定**，但 DOM 重建会令旧的 Element 引用和监听器全部失效（见 §2.7）。

**服务端绑定代码形态**（这是本项目打开炮塔 GUI 的唯一正确写法）：

```java
// 在服务端调用（例如右键底座的事件里）
ApricityUI.menu(serverPlayer, "screens/turret_base.html")
        .bind(binding -> binding
                .blockEntity(basePos)                                  // → HTML 里 id="block_entity"
                    .slot("#ammo_0").filter(FilterUtil.tag("turretdefense:ammo"))
                    .slot("#ammo_1").filter(FilterUtil.tag("turretdefense:ammo"))
                    // … 其余 4 个弹药槽同理
                    .slot("#module_0").filter(FilterUtil.tag("turretdefense:module"))
                    // … 其余 4 个插件槽同理
                .player());                                            // → HTML 里 id="player"
```

`FilterUtil` 可用：`ANY` / `NONE` / `EMPTY` / `item(Item)` / `tag(String)` / `custom(Predicate)` / `allOf` / `anyOf` / `not`，已有过滤器可用 `.and()` / `.or()` / `.negate()` 组合。
过滤器**只限制插入**，不限制取出，也不改变底层 Capability 的限制。
`.slot(selector)` 的 selector 是 CSS 选择器，匹配「最近声明的容器的直接子级 `<slot>`」；`#fuel` / `slot.fuel` / `slot[slot-index="0"]` 都合法，**不要求有 id**。

**高级入口**（本项目**暂不使用**，留作第二期多容器需求）：`ApricityScreenNetworkHandler.openScreen(player, path, declarations, argsById)`，可为每个 `ContainerDeclaration` 指定独立 id / 类型 / 容量 / primary 标志。注意：**此入口不支持槽位过滤规则**。

### 2.5 HTML / CSS 不支持清单

**没有浏览器默认样式（UA stylesheet）。** `<h1>` 和 `<div>` 长得一模一样，约 30 个标签是 inline、其余是 block，**所有样式必须自己写**。

**布局不支持：**

| 不支持 | 替代方案 |
|:---|:---|
| `float` | 用 `flex` |
| `table` 布局 | 用 `flex` 或手动定位 |
| `position: sticky` | 用固定定位 |
| Grid 的 `grid-area` / 自动流 / 命名线 | 用显式 `grid-template`（本项目槽位分区推荐用它） |
| 负 margin | 用 padding / transform 变通 |

**CSS 值解析缺口：**

- `calc()` **不支持乘除**（加减可用）
- 边框**只支持 `solid`**
- **无 `currentColor`**，写具体颜色值
- 命名颜色**只有 26 个**
- **无径向渐变、无锥形渐变**
- **无 `skew` / 矩阵变换**
- `font-style: italic` **无效** → 用 `oblique`
- `text-align: justify` **无效**
- `vertical-align` **只支持 baseline**

**CSS 选择器/规则不支持：** `:link` `:visited` `:target` `:lang()` `:dir()` `:has()`；`::first-line` `::first-letter` `::marker` `::selection`；`@supports` `@layer` `@page` `@container`。
`@media` **只支持** `min/max-width`、`min/max-height`、`orientation`。
`@font-face` **只取 `font-family` + 第一个 `src url()`**。

**HTML 解析器是正则分词器，不是标准树构建器：**

- **不做浏览器式隐式标签补全**（`<p>` 不会自动闭合、`<tbody>` 不会自动插入）→ **所有标签必须显式闭合**
- 只支持 **6 个命名实体**（`&amp;` 这类），其余请用数字实体或直接写 UTF-8 字符
- `<script src="...">` 同时又写内联内容时，**两者都会执行**（非标准行为）→ **绝不混写**
- 不支持 `defer` / `async` / `type="module"`

**表单：** `date` / `email` / `url` / `tel` / `search` / `time` 全部退化为文本框，无原生日历/取色/文件弹窗。

**其他：** 无 `srcset`、`alt` 不渲染、`<a>` 点击**只在系统浏览器打开链接**（不是页面内跳转）。

### 2.6 Rhino JavaScript 限制

**写法规范（必须遵守）**：用 `var` + 普通 `function` + 传统 `for` 循环。
AUI 会对部分现代语法做兼容转换，但 **Rhino 不是现代 JS 引擎，不要赌**。

**可用：** `window` `document` `console` `localStorage` `sessionStorage`、事件构造器、`performance.now()`、受限 `fetch`（仅 GET）、只读 `getComputedStyle`、`setTimeout`/`setInterval`/`requestAnimationFrame`、`URLSearchParams`（⚠️ **只有 `append`/`getAll`/`sort`/`forEach`/`toString`**，没有 `get`/`set`/`has`）、`FormData`、`ResizeObserver`/`MutationObserver`、`DOMMatrix`/`Path2D`/`OffscreenCanvas`、Canvas **2D only**。

**不可用：** `KeyboardEvent` 构造器、`navigator.clipboard`、`Selection`/`Range`、`history`、`matchMedia`、`XMLHttpRequest`、`WebSocket`、`IntersectionObserver`、`WebGL`、Service Worker、完整 Promise、`AbortController`、Shadow DOM、`postMessage`。

**键盘事件陷阱**：修饰键字段是 `controlKey`，**不是 `ctrlKey`**。这是从浏览器代码迁移时最常见的错误。

**事件系统是完整的**：capture / at-target / bubble 三阶段齐全。
支持的类型：`click dblclick contextmenu mousedown mouseup mousemove mouseover mouseout mouseenter mouseleave wheel scroll pointer* keydown keyup focus blur input beforeinput change submit reset formdata invalid select copy cut paste composition* DOMContentLoaded load unload resize`。
注意 `focus` / `blur` / 图片 `load`/`error` **不冒泡**。

### 2.7 线程与刷新代次（最易出崩溃的两条）

**① 全部 UI 状态都在客户端线程。**
Document、Element、布局、Screen、WorldWindow 全是客户端 UI 状态。从网络包回调、Future、线程池返回时，**必须先切回客户端线程**：

```java
Minecraft.getInstance().execute(() -> {
    var doc = ApricityUI.getDocument("screens/turret_base.html");
    if (doc != null && !doc.isEmpty() && doc.get(0).getElementById("status") != null) {
        doc.get(0).getElementById("status").setTextContent("ready");
    }
});
```

资源解码可以异步，**DOM 提交与纹理上传必须在客户端/渲染线程**。

**② `refresh()` 会重建整棵 DOM 树。**
你存下的 Element 引用、注册的事件监听器**全部失效**。异步回调必须存代次、回来验证：

```java
long generation = document.getRefreshGeneration();
Minecraft.getInstance().execute(() -> {
    if (!document.isCurrentGeneration(generation)) return;   // 已刷新，放弃
    Element el = document.getElementById("status");
    if (el != null) el.setTextContent("loaded");
});
```

**推论**：所有"在页面里长期存在的状态"（当前选中的塔头面、滚动位置）都要放在 **Kotlin 侧**，不要把状态留在 JS 变量里 —— 一次 `END` 重载就全没了。

### 2.8 KubeJS 绑定：把 Kotlin 方法暴露给页面 JS `[已核实]`

这是本项目的核心桥接机制。

```java
@KJSBindings(value = "TurretDefense", modId = "turretdefense", isClient = true)
public final class TurretDefenseBindings {
    private TurretDefenseBindings() {}

    // 页面里： TurretDefense.getCoreEnergy()
    public static int getCoreEnergy() { … }

    // 页面里： TurretDefense.upgradeHead(dirIndex)
    public static void upgradeHead(int dirIndex) { … }
}
```

在模组初始化阶段登记扫描包：

```java
KubeJS.scanPackage("com.turretdefense.ui.kjs");
```

**规则**：
- `value` 为空则用简单类名；`modId` 填了则只在对应模组加载时注册
- `isClient = true` 注册进客户端脚本，`false` 进服务端脚本 —— **这是注册过滤条件，不是侧安全保证**。客户端绑定类引用了 MC 客户端类时，绝不能注册到服务端
- 全局名会**自动带模组前缀**
- 失败用 `null` / `Optional` 表达，并在文档里写清楚
- 绑定方法保持 **public static**，参数与返回值用 **Rhino 能稳定转换的类型**（基本类型、String、简单集合）
- **不要把复杂的 DOM 遍历塞进脚本每帧调用**
- 改注解或扫描包后**必须重启客户端**

**设计分工（本项目强制）**：
- **JS 侧**：只负责**界面交互**（切换标签页、按钮点击、表单取值、局部显隐）
- **Kotlin 侧**：负责**一切游戏逻辑**（升级、切模式、读写数据、权限校验）
- **JS 绝不直接改世界状态**，一律 `TurretDefense.xxx()` 调过去，由 Kotlin 校验后执行

### 2.9 安全红线

页面 JS 在客户端 JVM 内执行，**没有任何沙箱**。

| 红线 | 说明 |
|:---|:---|
| **绝不加载第三方页面** | 只加载本模组 jar 内自带的 HTML。不接受 URL 参数、不接受服务端下发的任意路径 |
| **操作路径必须白名单校验** | 任何来自网络包/玩家输入的页面路径，必须比对白名单后才传给 AUI |
| **远程资源仅限图片/CSS/字体** | 远程 `<script>` 与远程 HTML **不会被下载执行**（框架已拦），但仍不要主动引用远程资源 |
| **不用 `<iframe>`** | 1.2.5 起 `<iframe>` 会调起操作系统 WebView，内存开销大，且只有硬件输入、无逻辑桥。本项目禁用 |

### 2.10 版本风险与应对

**风险事实**：ApricityUI 在 2026-08-06 → 2026-10-05 两个月内从 1.2.0 发到 1.2.7，共 8 个版本，changelog 里密集出现布局缓存正确性修复。**引擎仍在快速变动。**

**应对措施（必须执行）**：

1. **版本锁定**：`build.gradle` 与 `mods.toml` 里写死 `1.2.7`，不用动态版本范围。要升级时先读新版本 changelog。

#### 4.1.1 实现方式：一个 Block 类，5 个实例（关键）

**不要写 5 个 Block 类。** 正确做法是写**一个** `TurretHeadBlock` 类，
在注册时用不同的 `TurretKind` 参数实例化 5 次：

```kotlin
class TurretHeadBlock(val kind: TurretKind, props: Properties) : Block(props) { /* ... */ }

object ModBlocks {
    val PULSE_HEAD    = register("pulse_head",    TurretHeadBlock(TurretKind.Pulse,    HEAD_PROPS))
    val PARTICLE_HEAD = register("particle_head", TurretHeadBlock(TurretKind.Particle, HEAD_PROPS))
    val GRENADE_HEAD  = register("grenade_head",  TurretHeadBlock(TurretKind.Grenade,  HEAD_PROPS))
    val LASER_HEAD    = register("laser_head",    TurretHeadBlock(TurretKind.Laser,    HEAD_PROPS))
    val ARC_HEAD      = register("arc_head",      TurretHeadBlock(TurretKind.Arc,      HEAD_PROPS))
}
```

**这样做同时满足两个目标**：
- ✅ 所有者要的「每种炮塔是独立方块」—— 注册表里确实是 5 个方块，各有独立的模型、材质、语言条目、配方、物品形态
- ✅ 不产生 5 份重复代码 —— 逻辑全在一个类里，新增炮塔（第四期）只是多一行注册

**BlockEntity 同理**：只写**一个** `TurretHeadBlockEntity` 类，
用**一个 BlockEntityType 绑定全部 5 个方块**（MC 原生支持这种写法）：

```kotlin
val HEAD_BE = BlockEntityType.Builder
    .of(::TurretHeadBlockEntity,
        ModBlocks.PULSE_HEAD.get(), ModBlocks.PARTICLE_HEAD.get(),
        ModBlocks.GRENADE_HEAD.get(), ModBlocks.LASER_HEAD.get(),
        ModBlocks.ARC_HEAD.get())
    .build(null)
```

> **不要为每种炮塔写一个 BE 类。** 炮塔之间的行为差异由 `AttackBehavior` 策略对象承担（§5.5），
> 不是由 BE 类的继承层次承担。BE 类只负责「状态 + 调度 + 存档」。

#### 4.1.2 塔头的 BlockState 与渲染

| 属性 | 取值 | 用途 |
|:---|:---|:---|
| `FACING` | 6 个方向 | **指向底座**（贴在底座北面 → `FACING = SOUTH`） |
| `TIER` | 1–5 | 等级外观 |

每方块 30 个 BlockState，5 个方块共 150 个 —— 与单方块方案总量相同，完全安全。

**模型文件**：每个塔头方块 5 个模型（按 TIER），共 25 个，全部为 AI 可直接编写的 JSON。
`blockstate.json` 用 `x` / `y` 旋转覆盖 6 个朝向。

**首期仍然不写 `BlockEntityRenderer`**（§4.9），塔头用静态模型 + 粒子表现开火。

#### 4.1.3 两个 BlockEntity 的协作协议（**本节是难点，必须严格照做**）

塔头有独立 BE，就必然面对「两个 BE 互相引用」的经典难题。**必须用下面的协议解决，不要自行发明。**

**方向定义**：塔头的 `FACING` 指向底座；底座用 `Direction`（从底座指向塔头的方向）索引它。

**协议（四条，缺一不可）：**

**① 双向幂等注册**

```kotlin
// 在 TurretBaseBlockEntity 内
fun attachHead(dir: Direction, head: TurretHeadBlockEntity) {
    if (heads[dir] === head) return          // 幂等：重复注册直接返回
    heads[dir] = head
    head.bindBase(this, dir)
}

fun detachHead(dir: Direction) {
    heads.remove(dir)
}
```

**② 双方都要主动注册**（因为区块加载顺序不确定）

- 塔头 `onLoad()`：沿 `FACING` 找底座 → 找到则调 `base.attachHead(dir, this)~
- 底座 `onLoad()`：遍历 6 个方向找塔头 → 找到则调 `attachHead(dir, head)~
- 由于 `attachHead` 幂等，**两边都跑一遍是安全且必要的**

**③ 拆除时双方都要清理**

- 塔头 `setRemoved()`：`base?.detachHead(dir)~
- 底座 `setRemoved()`：遍历 `heads` 通知每个塔头 `unbindBase()~
- 底座被**破坏**时：范围内所有塔头**掉落为物品并消失**（不允许孤立塔头存在）

**④ 引用使用前必须校验**

```kotlin
val base = boundBase
if (base == null || base.isRemoved || base.level == null) { /* 重新解析或放弃本次操作 */ }
```

**绝对禁止**：在 `onLoad` 里假设对方已经加载；在 `tick` 里假设引用非空；靠 `neighborChanged` 单边维护关系。

> ⚠️ **这套协议的执行者自查方式**：造一个存档，反复执行「区块边界来回走动 / 拆底座 / 拆塔头 / 崩服重启」，
> 每次检查塔头与底座的绑定关系是否一致。**这是本项目最容易出隐蔽 bug 的地方。**

#### 4.1.4 为什么这个方案在第二期反而有优势

所有者选择的多方块方案，在第二期做瞄准动画时有一个天然优势：

`BlockEntityRenderer` 可以挂在**塔头自己的 BE** 上。这样：
- 每个渲染器只画 1 个塔头（而不是底座一次画 6 个）
- 天然享有 MC 的视锥裁剪与距离裁剪（BER 的 `shouldRender` 按方块位置判定）
- 动画状态存在塔头 BE 里，同步范围小

**代价是首期多了一套 BE 协作协议**（§4.1.3）。这是所有者已知情并接受的取舍。

#### 4.2.2 核心弹药库（**所有者决策：高级塔从核心扣弹**）

> **所有者原话**：「高级底座会直接从核心库存同步扣除」。

| 项目 | 规格 |
|:---|:---|
| 容量 | **18 格** |
| 过滤器 | 只接受 `#turretdefense:ammo` |
| 访问 | 任意 side（含 `null`）返回同一 handler，漏斗/AE2 可自动补给 |
| 扣除方式 | T4/T5 塔头开火时，经底座向核心请求扣 1 发**对应型号**的弹药 |
| 距离限制 | 仅核心管理半径内的底座可以扣弹 |

**扣弹流程（每次开火都要走）：**

```text
塔头 BE.fire()
  ├─ 需要弹药吗？（tier >= 4 且该炮塔有弹药定义）
  │    否 → 继续
  │    是 → 经 base 拿到核心引用
  │           ├─ 核心在管理半径内？
  │           ├─ 核心库存里有【该型号】的弹药？
  │           │     是 → 扣 1 发，继续开火
  │           │     否 → 本次开火失败，塔头停火 + 告警
```

**性能约束**：核心引用必须**缓存在底座 BE 里**，不允许每次开火都做世界查询。
弹药匹配用**物品标签**（`turretdefense:ammo/pulse_t4` 等），不要用字符串比对物品 id。

#### 4.2.4 核心殉爆（**所有者决策：提前到首期**）

| 项目 | 规格 |
|:---|:---|
| 触发条件 | **核心方块被破坏**（玩家挖掘），**或**核心生命值归零 |
| 范围 | 半径 **64 格**内的所有底座上的所有塔头 |
| 连锁方式 | 每座塔头间隔 **0.5 秒（10 tick）**依次爆炸 |
| 插件掉落 | 基础类 50% / 高级类 30% / 特殊类 10% |
| 弹药 | 弹药库中「爆炸弹」型被引爆，其余 50% 掉落 |
| 能量 | 全部释放（视觉表现 + 附近塔头受波动） |
| 底座 | **保留**（防爆），变为空底座 |
| 恢复 | 重新合成核心后，空底座**自动重新绑定** |

🔴 **爆炸铁律**：殉爆的每一次爆炸都是**纯伤害**，**不破坏任何方块**（§4.14）。
唯一被移除的方块是核心自己。

**实现约束**：
- 连锁用 `TickScheduler`（§5.9）驱动，**绝不用协程或 `Thread.sleep`**
- 64 格内可能有几十座塔头，全部炸完需要几十秒 —— 这是**有意为之的仪式感**，不要"优化"成一次性
- 殉爆期间核心 BE 已失效，调度器必须挂在 **Level** 上，并在维度卸载时清空

#### 4.2.5 核心状态机

| 能量占比 | 状态 | 塔头射速 | 修复 | 护盾 | 终焉裁决 |
|:---|:---|:---|:---|:---|:---|
| > 50% | 正常 | x1.0 | 正常 | 正常 | 正常 |
| 20%–50% | 节能 | x0.5 | x0.5 | 偏转效率降低 | 正常 |
| 5%–20% | 严重不足 | x0.25，**底座等级 >=T4 的高级塔停机** | x0.1 | 仅部分偏转 | 离线 |
| 1%–5% | 濒临耗尽 | 仅基础塔最低频率 | 停止 | 关闭 | 离线 |
| 0% | 休眠 | 全部停机 | 停止 | 关闭 | 离线（核心自充 1 FE/秒） |

**能量阈值必须做成配置项**（`lowThreshold` / `criticalThreshold` / `emergencyThreshold`）。

### 4.3 炮塔底座 `TurretBaseBlockEntity`

**BlockState：** `TIER` (1–5)。等级**必须能从 BlockState 读出**，这样客户端渲染不需要额外同步。

**底座等级的作用（已冻结）：**

| 底座等级 | 可装塔头面数 | 插件槽数 |
|:---|:---|:---|
| T1 | **1** | 1 |
| T2 | **2** | 2 |
| T3 | **3** | 3 |
| T4 | **4** | 4 |
| T5 | **6** | 5 |

**「可装面数」的含义**：底座在世界上有 6 个面，但只有其中 **N 个面**允许安装塔头。
允许哪些面由安装顺序决定：**前 N 个成功安装的面被占用**，与具体方向无关。
已占用的面在 GUI 与准星提示里要高亮显示。

**底座的不可损毁性：**
底座**免疫一切伤害**：爆炸、怪物攻击、火焰、水、活塞推动。
实现：`BlockBehaviour.Properties` 里设爆炸抗性为极大值 + 在伤害事件里直接跳过底座（§4.14.3）。
**塔头是唯一的可损毁部分。**

**底座的 `IItemHandler` 布局（关键，不得改动索引）：**

| 局部索引 | 用途 | 数量 | 是否加物品过滤器 |
|:---|:---|:---|:---|
| 0 – 4 | 插件槽（该底座最多 6 个塔头共享） | 5 | ✅ `#module_0` … `#module_4` |
| 5 – 31 | 战利品缓存（塔头共享） | 27 | ❌ 任意物品 |

**总容量固定 32 格。**

> 🔴 **本节已按所有者决策修订**：所有者选择「高级底座直接从核心库存扣弹」，
> 因此**底座不再有弹药槽**，容量从 38 格缩减到 32 格。执行者不要自行加回弹药槽。
>
> **为什么槽位必须手写 `<slot>`**：只有手写槽位才能挂 `FilterUtil` 过滤器。
> 自动生成的槽位没有稳定 id，**无法过滤**（§2.4 第 ④ 条）。
> **因此 32 个槽位必须全部手写**，一个都不能靠自动生成。

**底座的可访问性：**
`getCapability(ITEM_HANDLER_CAPABILITY, side)` **对任意 `side`（含 `null`）都返回同一个 handler**。
这样漏斗、AUI 容器、将来 AE2 都能正常访问。

**底座的 `IEnergyStorage`：** 只接收，不输出。由核心推送能量。

**底座对核心的引用（弹药扣除必需）：**
底座 BE 缓存所绑定核心的引用，**在绑定时刷新**（§4.4），不允许每次扣弹都做世界查询。
塔头通过底座拿到核心，不自己找核心。

**底座 BE 的 tick 职责**：能量接收、缓存传输（每 100 tick）、绑定校验（每 100 tick）。
**底座不驱动塔头开火** —— 塔头自己调度（§4.12.2）。

### 4.4 底座、塔头与核心的绑定机制（性能关键）

> **绝不允许核心逐方块扫描来找底座。** 128 格半径逐方块 = 200 万次检查，服务器直接死。

**① 世界级注册表 `TurretNetworkData : SavedData`**
记录所有核心的 `BlockPos`（按维度分组）。核心放置时登记，破坏时注销。

**② 底座放置时主动绑定**
`setPlacedBy` 里读取 `TurretNetworkData` → 在管理半径内找**最近的核心** → 调 `core.registerBase(this.pos)`。
绑定成功后**立刻缓存核心引用**（§4.3）。

**③ 核心放置时反向补齐**
核心放置时，遍历管理半径内的**所有已加载区块**，用 `LevelChunk.getBlockEntities()` 拿到区块内全部 BE，筛出底座并注册。
> 这正是不能用逐方块扫描的原因：`getBlockEntities()` 的成本是「区块数 x 平均 BE 数」（通常几千次），而不是「体积」（200 万次）。
> 128 格半径 = 17x17 = 289 个区块。**必须分帧执行**（每 tick 处理若干区块），不要在一次调用里跑完。

**④ 失联清理**
- 核心每 5 秒遍历一次 `managedBases`，跳过未加载的区块，清理已消失的底座
- 底座每 5 秒校验一次绑定的核心是否还在；不在则尝试重新绑定

**⑤ 塔头与底座的绑定**
见 §4.1.3 的双向幂等注册协议。**核心不直接管塔头** —— 核心只管底座，底座管塔头。

### 4.5 集中式索敌（性能核心之一）

> **决策 14**：只有核心扫描，塔头不做任何实体查询。

**扫描流程（每 `scanIntervalTicks` 一次，默认 20 tick）：**

```text
核心.onScanTick()
  ├─ ⓪ 前置闸门：managedBases 里是否存在【至少一个有待机塔头】的底座？
  │     否 → 本轮直接返回（零成本，夜里/无敌人时开销归零）
  ├─ ① 收集候选：level.getEntitiesOfClass(Monster::class.java, scanAABB, selector)
  │     scanAABB = 核心位置 ±scanRadius（默认 = 管理半径 = 128）
  │                Y 轴裁剪为 ±scanVerticalRange（默认 64）
  ├─ ② 计算到核心的距离平方，升序排序 → 得到候选数组
  ├─ ③ 预算每个候选到核心的 distSqrToCore: DoubleArray（避免重复开方）
  ├─ ④ 打包成 ThreatSnapshot（存 Entity 引用/ID，【绝不存坐标快照】）
  └─ ⑤ 下发给每个已注册底座；底座再转发给它自己的塔头
```

**`ThreatSnapshot` 的内容约束：**

| 允许 | 禁止 |
|:---|:---|
| `Entity` 引用（弱引用语义，用 ID 校验存活） | ❌ 坐标快照（`Vec3` 数组） |
| 排序后的索引数组 | ❌ 每 tick 重建的集合 |
| 预先算好的 `distSqrToCore` | ❌ 保存 `AABB` 或世界查询结果 |

**为什么绝不存坐标快照**：实体在两次扫描之间会移动几十格。
若塔头用陈旧坐标判定射程，会出现"打到了射程外的敌人"或"射程内的敌人打不到"。
**正确做法**：塔头在**开火瞬间**重新读 `entity.position()` 并校验
`entity.isAlive() && !entity.isRemoved()`。距离比较一律用**平方距离**，不开方。

**性能优化：三角不等式剪枝**
塔头按顺序遍历候选数组。若「核心到候选 i 的距离」已经超出「塔头到核心的距离 + 塔头射程」，
则后续所有候选都更远，**直接 break**。这利用了候选按距核心距离升序排列的性质。

**性能优化：目标粘性**
每个塔头记住当前目标。只要目标仍存活、仍在射程内，**不换目标**。
- 手感收益：不会因为一个更近的敌人路过就放弃快打死的目标
- 性能收益：尸潮持续进攻时，绝大多数塔头每轮扫描都不需要遍历候选数组
- 实现：用**身份语义**的集合（`fastutil ObjectOpenHashSet` 或 `Collections.newSetFromMap(IdentityHashMap())`），
  **绝不用普通 `HashSet`**（会走 `equals`，对 Entity 极其昂贵）

**自适应降频**（与 §4.13.11 措施 4 配合）：
- 候选实体数 > `highLoadEntityCount`（默认 150）→ 扫描间隔翻倍
- 候选实体数 < `lowLoadEntityCount`（默认 50）→ 间隔减半
- 区间：`[10, 40]` tick
- **另有一条按真实耗时降频的规则**（§4.13.11 措施 4），两者取更保守的

### 4.7 战利品链路

**完整链路（首期必做，不是"以后再说"）：**

```text
敌人死亡
  ├─ LivingDropsEvent      → cancel 原版掉落物生成，改投递到击杀者的底座缓存
  ├─ LivingExperienceDropEvent → cancel 经验球，按 7 XP = 1 附魔之瓶压缩
  └─ 若缓存 27 格已满 → 停止接收 + 30 秒节流的一次告警（不刷屏）
底座缓存
  └─ 每 100 tick 检查一次，把物品传输到核心
核心
  └─ 存入核心的物品缓冲区；满则停止并告警
```

**关键实现点：**

| 点 | 要求 |
|:---|:---|
| 击杀者归属 | 从 `DamageSource.getEntity()` 反查是哪座塔头造成的伤害 |
| 掉落物去向 | 通过塔头 → 底座 → 该底座缓存；**不是**掉在地上 |
| 经验压缩 | `pendingXp` 累计，满 7 点产 1 瓶附魔之瓶 |
| 缓存满 | 停止接收，**不再产生新物品**（而不是掉落在地上） |
| 传输节流 | 每 100 tick 一次，不是每 tick |
| 性能 | 高频击杀时，**不要每次击杀都做世界查询** —— 击杀者信息在伤害时已记录 |

> **为什么经验要压缩成瓶**：尸潮中一次战斗可能产生上千个经验球，
> 每个经验球都是一个实体 + 一次客户端同步。压缩成瓶子后数量减少 7 倍，且瓶子可堆叠。

### 4.8 伤害来源、护盾与塔头损毁

#### 4.8.1 三条伤害来源（**必须自建，原版没有**）

> 🔴 **这是原设计文档最大的漏洞**：原文档假设「炮塔会被攻击、有生命值和护盾」，
> 但**原版 Minecraft 的怪物根本不攻击方块**。这个伤害来源在游戏里不存在。
> 不补的话，「护盾」与「塔头生命值」就是永远触发不了的死设定。

| # | 来源 | 实现 |
|:--:|:---|:---|
| ① | **怪物主动攻击炮塔** | `EntityJoinLevelEvent` 时给 `Monster` 注入 `TurretAttackGoal` |
| ② | **爆炸伤害** | `ExplosionEvent.Detonate`（§4.14.3） |
| ③ | **弹射物命中** | `ProjectileImpactEvent` |

**关于 ①（默认开启，所有者已确认「会攻击，无需额外配置」）：**

| 要求 | 说明 |
|:---|:---|
| 目标 | 只有 `Monster` 子类获得该 Goal |
| 优先级 | **必须低于原版的玩家索敌**（玩家永远是第一优先），否则怪物会无视玩家去拆塔 |
| 触发距离 | 怪物 16 格内存在塔头 |
| `canUse()` | **绝不允许在这里遍历实体** —— 用附近方块查询或缓存（§4.10.4） |
| 攻击 | 走正常近战伤害流程，伤害落到【塔头】身上 |

#### 4.8.2 底座与塔头的受击规则

| 对象 | 规则 |
|:---|:---|
| **底座** | **完全免疫**。伤害事件里直接跳过；爆炸事件里从 `affectedBlocks` 移除（§4.14.3） |
| **核心** | 可受伤。生命值归零 → 方块移除 + **触发殉爆**（§4.2.4） |
| **塔头** | 可受伤。生命值归零 → **爆炸 + 掉落 + 消失**（§4.14.4） |

#### 4.8.3 护盾（次数制）

**护盾是「层数」，不是「第二管血」。**

```text
受到伤害 N 点：
  if (shieldLayers > 0) {
      shieldLayers -= 1        // 1 层挡 1 次攻击
      // 伤害被【完全抵消】，不扣生命值
  } else {
      health -= N              // 正常扣血
      if (health <= 0) 塔头爆炸 + 掉落 + 消失
  }
```

> **护盾数值本身是 `[待定]`**（§6.5）：按原文档数值，T5 炮塔 61 层 = 61 次完全免疫，等于无敌。
> 所有者已声明「数值以后处理」，因此**按原文档数值实现，全部做成配置项**，
> **执行者不要自行重定标**，也不要预先把候选方案 A/B/C 实现出来。

#### 4.8.4 塔头被摧毁时的行为

1. 在塔头位置播放爆炸粒子与音效（**纯视觉，不破坏方块**，§4.14）
2. 掉落：**部分**插件与在装弹药（比例见 §6 配置）
3. 塔头方块移除
4. 底座**保留**，该面变为空闲，可以重新安装塔头
5. 通知底座与核心更新状态

### 4.9 客户端渲染与同步（性能优先 → 无 BER 方案）

#### 4.9.1 方案：不用 `BlockEntityRenderer`

**塔头用标准的 BlockState 模型渲染**（方块状态驱动 `blockstate.json`），
**首期不写任何 `BlockEntityRenderer`**。

| 项目 | 做法 |
|:---|:---|
| 塔头外观 | 25 个模型 JSON（5 种炮塔 x 5 等级），按 `FACING` / `TIER` 切换 |
| 朝向 | 由 `FACING` 的 `x` / `y` 旋转覆盖，**不做平滑转向** |
| 开火表现 | **纯粒子 + 音效**（§6.9），全部服务端发指令、客户端播放 |
| 同步 | 塔头的 `kind` / `tier` / `facing` **全部派生自 BlockState**，天然同步，零额外网络包 |

**收益**：
- 方块模型可被 MC 原生合批，而 BER 不能
- **同步层几乎为零** —— 首期基本不需要自定义 S2C 网络包
- 塔头 BE 的数据只在服务端使用，不需要 `getUpdatePacket`

**代价**：炮塔不会转头瞄准。所有者已知情并接受（首期不做，第二期评估）。

#### 4.9.2 第二期的优势（多方块方案的回报）

因为所有者选择了「每种炮塔一个方块」，第二期做瞄准动画时可以用**挂在塔头 BE 上的 BER**：
- 每个渲染器只画 1 个塔头（而不是底座一次画 6 个）
- 天然享有 MC 的视锥裁剪与距离裁剪
- 动画状态存在塔头 BE 里，同步范围小
- **必须带距离裁剪**（24 格外不渲染），否则动画会吃掉首期的全部性能收益

#### 4.9.3 禁止事项

- ❌ 首期写 `BlockEntityRenderer`
- ❌ 每 tick 发送自定义网络包
- ❌ 在渲染路径里解析字符串 / 新建纹理
- ❌ 用 `DynamicTexture` 动态生成贴图

### 4.10 性能预算与红线

#### 4.10.1 目标场景

**「工业基地中打尸潮」**：大量方块实体（其他模组的机器） + 200~500 个敌对实体同时进攻。
这是本项目性能设计的**唯一靶子**。

#### 4.10.2 各组件 tick 频率总表

| 组件 | 做什么 | 频率 |
|:---|:---|:---|
| 核心 | 能量生产/分配 | 每 5 tick |
| 核心 | **集中扫描** | 每 20 tick（自适应 10–40） |
| 核心 | 底座注册表校验 | 每 100 tick（5 秒） |
| 核心 | 终焉裁决条件判定 | 复用扫描结果，零额外成本 |
| **底座** | 能量接收、缓存传输、绑定校验 | 每 100 tick |
| **塔头** | 到期检查（一次 long 比较） | **每 tick，但只比较不做事**（§4.12.2） |
| 塔头 | 实际开火 | 冷却到期时（§6.3 各塔冷却） |
| 塔头 | 护盾再生判定 | 每 20 tick |

#### 4.10.3 明确不做的事（性能红线）

| ❌ 禁止 | 原因 |
|:---|:---|
| 核心逐方块扫描找底座 | 200 万次检查（§4.4） |
| 塔头自己做实体查询 | N 个塔头 x M 个实体 = 爆炸（§4.5） |
| 开火时在世界里查询实体 | 必须复用候选列表（§4.13.6） |
| 生成弹射物实体 | 尸潮中每秒数百个实体 |
| 每 tick 发送自定义网络包 | 带宽与 GC |
| 每 tick 向所有玩家发粒子 | 粒子是客户端成本（§4.13.7） |
| 每 tick 新建 `ItemStack` / `AABB` / 集合 | GC 压力 |
| 在 `Goal.canUse()` 里遍历实体 | 每 tick 每怪物调用一次 |
| 在 tick 里遍历区块方块实体 | 分帧或改用事件（§4.13.8） |

#### 4.10.4 对象复用要求

- 距离比较一律用**平方距离**（`distanceToSqr`），只在需要显示时才开方
- 扫描产生的候选数组**复用同一个缓冲区**，不每轮新建
- 塔头缓存自己的 `TurretStats` 引用，不每次开火去查表
- `AABB` 在扫描时复用（`setMinMax` 修改而非新建）

### 4.12 事件驱动调度（替代 tick 分片）

#### 4.12.1 为什么不采用 tick 分片

常规分片做法：把 32 个底座按坐标哈希分到 4 个 tick 槽位，每个底座每 4 tick 处理一次。
**问题**：
- **射速精度崩坏**：粒子炮塔 T5 射速 0.3 秒 = 6 tick，4 tick 的粒度意味着 33% 误差
- 而且**绝大多数 tick 是空转**：塔头没到冷却时间，检查了也没事做

#### 4.12.2 采用方案：塔头 BE 自调度

> 我原本设计的是「底座维护一个到期时间最小堆」。
> 但所有者选择了**每种炮塔一个方块**，塔头有了**自己的 BE** ——
> 于是每个塔头天然就是一个独立的调度单元，**优先队列不再需要**。

**每个塔头 BE 自己注册 ticker，只做一次比较：**

```kotlin
val TICKER = BlockEntityTicker<TurretHeadBlockEntity> { level, pos, state, be ->
    if (level.isClientSide) return@BlockEntityTicker
    val now = level.gameTime
    if (now < be.nextFireTick) return@BlockEntityTicker   // 绝大多数 tick 走这一行，O(1)
    be.tryFire(now)
}
```

**收益：**
- **射速精度 = 1 tick**（完美，无任何误差）
- **待机成本 = 一次 long 比较**（比堆顶比较还便宜，且无需维护堆结构）
- **开火逻辑写在塔头自己身上**，与「每种炮塔一个方块」的心智模型一致
- 省掉了底座侧「遍历 6 个塔头 / 维护优先队列」的全部代码

**代价（必须接受）**：192 个塔头 = 每 tick 192 次 ticker 调用。
每次只是一次 `gameTime` 读取与一次 long 比较，实测成本在微秒级，**可接受**。

> ⚠️ **不得改回「底座按坐标哈希分片」**。分片会让粒子炮塔（T5 冷却 6 tick）产生 33% 射速误差。

**底座 BE 的 tick 职责（与塔头分离）**：能量接收、缓存传输（每 100 tick）、绑定校验（每 100 tick）。
**底座不负责驱动塔头开火。**

#### 4.12.3 弹道全部改为 hitscan（零弹射物实体）

**决策：首期不生成任何弹射物实体。**

| 弹道类型 | 实现 |
|:---|:---|
| 直线 / 穿透 | 立即 raycast 命中 |
| 电弧连锁 | 立即在候选列表里跳跃 |
| 持续光束（激光） | 每 2 tick 结算一次，同样零实体 |
| **抛物线（榴弹）** | **延迟队列**：记录落点与延迟 tick，到期结算 AOE |

**榴弹的飞行时间保留**（12 tick，可配置）—— 这是玩法（敌人能躲），
但用 `TickScheduler` 的延迟任务实现，**不生成实体**。

#### 4.12.4 粒子与音效节流

- 每个底座**每 tick 最多 1 个音效**，每秒最多 4 个
- 音效只播放给 48 格内的玩家
- 粒子按距离抽稀（§4.13.7）

### 4.13 极端场景性能方案（工业基地 + 尸潮）

> 本节是「性能第一」原则的落地。**每一条都是设计约束，不是"以后优化"的选项。**

#### 4.13.1 优化一：候选排序 + 三角不等式剪枝

扫描结果按「到核心的距离」升序排列。塔头遍历时：
若「核心到候选 i 的距离平方」> 「塔头到核心距离 + 塔头射程」的平方 → **直接 break**。
利用了排序性质，把 O(n) 遍历降到通常 O(1~k)。

#### 4.13.2 优化二：目标粘性

塔头记住当前目标，只要它活着且在射程内就不换（§4.5）。
- 手感：不会因为更近的敌人路过就放弃快打死的目标
- 性能：尸潮持续进攻时**绝大多数塔头每轮扫描不需要遍历候选**
- 必须用**身份语义集合**（Identity），不用普通 `HashSet`$

#### 4.13.3 优化三：自适应扫描降频

两条规则同时生效，**取更保守的那个**：
1. 按候选实体数：> 150 翻倍，< 50 减半，区间 `[10, 40]` tick
2. **按真实耗时**：单次扫描 > `scanCostBudgetMs`（默认 3.0 ms）→ 间隔翻倍（§4.13.11 措施 4）

上限 40 tick（2 秒），不会无限降频把炮塔变成瞎子。

#### 4.13.4 优化四：无待机塔头则完全跳过扫描

核心先检查 `managedBases` 里是否存在「至少一个有待机塔头」的底座。
**不存在 → 本轮完全不扫描**，零成本。这在夜里、无敌人时让核心开销归零。

#### 4.13.5 优化五：单 tick 开火数硬上界（防雪崩的关键）

```kotlin
// 全局计数器，在每个 ServerTickEvent 开头清零
var firedThisTick = 0

// TurretHeadBlockEntity.tryFire(now) —— 由塔头自己的 ticker 调用（§4.12.2）
fun tryFire(now: Long) {
    if (firedThisTick >= Config.maxFiresPerTick) {   // 默认 64，全服务器级
        nextFireTick = now + 1                       // 本 tick 预算用完，推迟 1 tick 再来
        return
    }
    if (!fire()) {                                   // fire() 返回 false = 缺弹药 / 缺能量 / 无目标
        nextFireTick = now + 20                      // 1 秒后重试，避免每 tick 空转
        return
    }
    nextFireTick = now + cooldownTicks()             // 激光塔为 +2，其余按 §6.3 冷却表
    firedThisTick++
}
```

**为什么必须有**：1000 个塔头在尸潮中可能因冷却同步而在同一 tick 同时到点。
没有上界 = 单 tick 内 1000 次 raycast + 1000 次 `entity.hurt()` + 1000 次粒子广播。

**代价**：极端超载时射速会下降（但不会崩服）。这是**有意的取舍**。

#### 4.13.6 优化六：开火时零世界查询

塔头开火时**只允许**做：
1. 从缓存的候选列表里取目标
2. 读 `entity.position()`（内存读取，非世界查询）
3. 校验 `isAlive() && !isRemoved()`
4. 算平方距离、`hurt()`、发粒子指令

**绝不允许**在开火路径里出现 `getEntities` / `clip` / `getBlockState` 的循环。

#### 4.13.7 优化七：粒子批处理与距离抽稀

| 到玩家距离 | 粒子点数 |
|:---|:--:|
| < 16 格 | 12 |
| 16–32 格 | 8 |
| 32–64 格 | 4 |
| > 64 格 | **0** |

- 同一 tick 内多个塔头的粒子**合并成一次 `sendParticles`**（按类型分组）
- 绝不对每个玩家单独发送

#### 4.13.8 优化八：分帧执行长任务

以下任务**必须分帧**（每 tick 做一部分）：
- 核心放置时的 289 区块扫描（每 tick 若干区块）
- 殉爆连锁（每 10 tick 一座塔头，用 `TickScheduler`）
- 缓存传输（每 100 tick 一次，不是每 tick）

#### 4.13.9 优化九：多核心不共享

多核心各自独立扫描，**不做跨核心共享**。理由是共享需要全局协调，复杂度远超收益。
背靠背的两个核心会各扫一次，但各自的扫描半径受 `scanRadiusCap` 限制（默认 128）。

#### 4.13.10 性能探针（决策 30，验收必做）

`/turretdefense perf` 命令必须输出：

| 指标 | 说明 |
|:---|:---|
| 核心数 / 底座数 / 塔头数 | 规模统计 |
| 本轮扫描实体数 | 候选规模 |
| 扫描单次耗时（平均/峰值） | **真实耗时**，不是估算 |
| 当前扫描间隔 | 是否触发了降频 |
| 已触及 `maxFiresPerTick` 上界的次数 | 判断上界是否设得太小 |
| 本模组 MSPT 增量（平均/峰值） | 最终指标 |
| 粒子发送次数 / tick | 客户端成本代理指标 |

#### 4.13.11 如何支撑 128 格满半径扫描（**所有者明确要求**）

> 所有者否决了「扫描半径封顶 64 格」的提议，要求**炮塔必须能打满 128 格**。

**先纠正一个我自己的估算错误。**

我最初把「128 格半径」等同于「289 个区块全部要遍历」，这是**错的**。真实成本模型是：

| 事实 | 说明 |
|:---|:---|
| MC 用 `EntitySection` 存实体 | 每个 16x16x16 的小段一个列表，**空段根本不在数据结构里** |
| `getEntitiesOfClass` 的遍历量 | 约等于 **O(AABB 覆盖的非空段数 + 命中实体数)**，**不是** O(体积) |
| 128 格 AABB | 16x16 = 256 个区块列，但每列平均只有 **1–3 个非空实体段** |
| 实际遍历量 | 几百到一千次结构访问 + M 个实体的类型判断 |
| 结论 | 单次扫描是**亚毫秒级** |

**所以 128 格满半径扫描是可行的。** 下面六项措施用于把最坏情况压住。

**措施 1：Y 轴裁剪（最有效）**
AABB 垂直范围限制为核心上下各 **64 格**（`scanVerticalRange`，默认 64）。
128 格水平半径 + 无限制垂直范围会变成 256x384x256 的巨盒，那才是灾难。
裁剪后体积减少到约 1/3，**不影响实际战斗**（炮塔打不到 64 格外的高空）。

**措施 2：128 格时默认降频**
`scanIntervalTicks` 基础默认值改为 **20 tick（1 秒）**，而不是 10 tick。
128 格交战距离下，0.5 秒与 1 秒的索敌延迟玩家感知不到，但扫描成本直接减半。
**这是零代价的性能收益。**

**措施 3：无待机塔头则完全跳过扫描**（同 §4.13.4）

**措施 4：单次扫描耗时超阈值 → 自动加长间隔**

```kotlin
val t0 = System.nanoTime()
val snapshot = doScan()
val costMs = (System.nanoTime() - t0) / 1_000_000.0
if (costMs > Config.scanCostBudgetMs) {        // 默认 3.0 ms
    currentInterval = min(currentInterval * 2, MAX_SCAN_INTERVAL)   // 上限 40 tick
    logDebug("scan cost %.2f ms, interval -> %d", costMs, currentInterval)
}
```

**这比"按实体数降频"更直接** —— 它测的是**真实耗时**，而不是代理指标。

**措施 5：分帧扫描（仅在实测不达标时启用）**
把 128 格 AABB 沿 X 轴切成 2 或 4 片，每 tick 扫一片，2–4 tick 拼成完整快照。
代价：快照**有撕裂**。影响可接受（开火时读的是实时位置，快照只用于粗筛）。
**这是兜底方案，不要一上来就实现。**

**措施 6：可配置的最后退路**
`scanRadiusCap` 默认 **128**（不限制）。若服务器依然吃力，服主可自行调低到 64/96。
**执行者不得擅自修改这个默认值。**

**性能验收要求（§9 已同步）**
必须在 **128 格满半径 + 400 敌对实体 + 200 塔头** 下实测：

| 指标 | 通过标准 |
|:---|:---|
| 核心扫描单次耗时 | 平均 < 1.5 ms，峰值 < 4 ms |
| 高负载降频是否生效 | 日志里必须能看到降频记录 |
| 本模组 MSPT 增量 | 平均 < 0.5 ms，峰值 < 2 ms |

> ⚠️ **诚实声明**：上面的成本模型是基于 MC 实体存储机制推导的**设计估算**，**未经过实测**。
> 若实测不达标，按措施 5 → 措施 6 顺序逐级启用，**并向所有者报告，不要偷偷改小默认值**。

### 4.14 爆炸铁律（**所有者硬性约束**）

> **所有者原话**：「只有爆炸伤害，没有爆炸方块的能力。所有涉及爆炸的地方，不要摧毁方块，只伤害。」
>
> 这一条**没有任何例外**。本项目里的每一次爆炸都必须是「纯伤害爆发 + 视觉效果」，
> **不允许改变世界中的任何一个方块**（包括地形、其他模组的方块、我们自己的方块）。

#### 4.14.1 覆盖范围

| 场景 | 位置 | 要求 |
|:---|:---|:---|
| 榴弹 AOE | §6.3.3 | 只伤害范围内实体 |
| 引力迫击 AOE | 附录 A | 只伤害范围内实体 |
| 自爆核心插件 | §6.8 | 只伤害范围内实体 |
| 塔头被摧毁 | §4.8.4 | 只伤害范围内实体 |
| **终焉裁决** | §4.2.3 | 只伤害范围内实体 |
| **核心殉爆** | §4.2.4 | **每一次连锁爆炸都只伤害** |
| 爆炸弹头 / 集束弹头等插件 | 附录 B | 只伤害范围内实体 |
| 其他模组/原版的爆炸波及我们 | 本节 | 不摧毁我们的方块，但**可以伤害塔头与核心** |

#### 4.14.2 正确实现：纯伤害扩散

**绝不要调用 `level.explode(...)`** —— 那个 API 会破坏方块。

统一使用下面的辅助函数（放在 `com.turretdefense.util.ExplosionUtil`）：

```kotlin
/**
 * 纯伤害爆炸：只伤害实体，绝不改变任何方块。
 * 这是本项目唯一允许的「爆炸」实现方式。
 */
fun damageOnlyExplosion(
    level: ServerLevel,
    center: Vec3,
    radius: Double,
    damage: Float,
    source: DamageSource,
    knockback: Double = 0.4,
    maxTargets: Int = 64,          // 性能闸门：单次爆炸最多影响 64 个目标
) {
    val aabb = AABB(center, radius, radius, radius)
    var hit = 0
    for (entity in level.getEntities(null as Entity?, aabb)) {
        if (hit >= maxTargets) break
        if (!entity.isAlive || entity.isRemoved || entity.isSpectator) continue
        if (entity is Player && entity.isCreative) continue
        val d = entity.position().distanceTo(center)
        if (d > radius) continue
        val falloff = (1.0 - d / radius).coerceIn(0.0, 1.0)   // 距离衰减
        entity.hurt(source, (damage * falloff).toFloat())
        if (knockback > 0.0) {
            val dir = entity.position().subtract(center)
            if (dir.lengthSqr() > 1.0E-6) {
                val n = dir.normalize()
                entity.push(n.x * knockback, n.y * knockback * 0.5, n.z * knockback)
            }
        }
        hit++
    }
    // 视觉与音效照常播放（这些不改变世界）
    level.sendParticles(ParticleTypes.EXPLOSION, center.x, center.y, center.z, 1, 0.0, 0.0, 0.0, 0.0)
    level.playSound(null, center.x, center.y, center.z,
        SoundEvents.GENERIC_EXPLODE, SoundSource.BLOCKS, 1.0f, 1.0f)
}
```

**注意**：这个函数里的 `getEntities` 是**唯一的例外**，允许在爆炸时查询实体。
但因为有 `maxTargets` 上限和半径限制，成本可控。
**不要**把这套用法推广到炮塔开火上 —— 开火仍必须复用候选列表（§4.13.6）。

#### 4.14.3 防御外部爆炸：我们的方块永不被炸毁

```kotlin
@SubscribeEvent
fun onExplosionDetonate(event: ExplosionEvent.Detonate) {
    val level = event.level
    val ourBlocks = mutableListOf<BlockPos>()

    val it = event.affectedBlocks.iterator()
    while (it.hasNext()) {
        val pos = it.next()
        val block = level.getBlockState(pos).block      // getBlockState 比 getBlockEntity 便宜
        if (block is TurretBaseBlock || block is TurretHeadBlock || block is BaseCoreBlock) {
            ourBlocks.add(pos)
            it.remove()                                  // 关键：从受影响列表移除 -> 不会被摧毁
        }
    }

    if (ourBlocks.isEmpty()) return

    // 现在只对这些位置施加【伤害】，不摧毁方块
    // 底座：完全免疫，跳过
    // 塔头：按爆炸强度扣生命值与护盾
    // 核心：按爆炸强度扣生命值；归零则触发殉爆（§4.2.4）
    applyExplosionDamageToTurrets(level, ourBlocks, event.explosion)
}
```

**两个必须注意的细节**：
1. 用 `level.getBlockState(pos).block` 判断，**不要**用 `getBlockEntity`（后者会创建/加载 BE 对象，昂贵）
2. 用 `Iterator.remove()` 而不是 `removeIf`（`affectedBlocks` 是 `ArrayList`，迭代器删除更省）

#### 4.14.4 「摧毁」的唯一合法途径

| 对象 | 消失方式 |
|:---|:---|
| **底座** | **永不消失**（除玩家自己挖） |
| **塔头** | 生命值归零 → **自己掉落为物品并消失**（不是被炸掉的） |
| **核心** | 生命值归零 **或** 被玩家挖掉 → 方块移除 + **触发殉爆** |
| **地形** | **永远不变**。我们的任何效果都不会在世界上留下坑洞 |

> ⚠️ **验收方式**：在平地上放满炮塔，引爆所有能引爆的东西（榴弹、自爆核心、终焉裁决、殉爆），
> 结束后**地形必须与爆炸前逐方块完全一致**。这是 §9 的一条硬性验收项。

#### 4.14.5 为什么这条约束是合理的

1. **玩家的基地是心血** —— 炮塔防御本来是为了保护基地，结果自己的爆炸把基地炸了，体验极差
2. **性能** —— 破坏方块会触发光照更新、区块重算、客户端重绘，是 MC 里最昂贵的操作之一
3. **兼容性** —— 不碰方块就不会与其他模组的保护插件、领地系统冲突
4. **可回滚** —— 纯伤害不会留下无法恢复的世界改动

### 5.3 炮塔类型：用 sealed class 而不是 enum

```kotlin
sealed class TurretKind(
    val id: String,
    /** T1..T5，索引 0..4 */
    val stats: List<TurretStats>,
    val behavior: AttackBehavior,
    /** 该炮塔的 T4/T5 弹药；null 表示仅耗能（如激光） */
    val ammoT4: String? = null,
    val ammoT5: String? = null,
) {
    object Pulse    : TurretKind("pulse",    TurretStatsTable.PULSE,    HitscanBehavior,          "ammo_iron_slug",     "ammo_pulse_core")
    object Particle : TurretKind("particle", TurretStatsTable.PARTICLE, HitscanBehavior,          "ammo_particle_clip", "ammo_hv_particle_clip")
    object Grenade  : TurretKind("grenade",  TurretStatsTable.GRENADE,  BallisticBehavior,        "ammo_grenade",       "ammo_he_grenade")
    object Laser    : TurretKind("laser",    TurretStatsTable.LASER,    ContinuousBeamBehavior,   null,                 null)
    object Arc      : TurretKind("arc",      TurretStatsTable.ARC,      ChainBehavior,            "ammo_arc_cell",      "ammo_hv_arc_cell")

    companion object {
        val ALL: List<TurretKind> = listOf(Pulse, Particle, Grenade, Laser, Arc)
        private val BY_ID = ALL.associateBy { it.id }
        fun byId(id: String): TurretKind? = BY_ID[id]
        fun byOrdinal(index: Int): TurretKind = ALL[index]
    }
}
```

**为什么用 `sealed class` + `object` 而不是 `enum class`：**
- `enum` 的每个常量必须参数完全一致；将来某个炮塔需要额外字段（如狙击塔的「穿透数」）时，`enum` 会逼你给所有塔都加这个字段
- `sealed class` 允许子类各自持有不同字段，且 `when` 表达式**仍然可以穷尽检查**
- 将来加"自定义炮塔"时，`sealed` 的限制是好的（编译器会提醒你处理新分支）

**「byOrdinal」的存在是为了 BlockState**：`TurretHeadBlock` 的 `KIND` 属性是 `EnumProperty<TurretKindProperty>`，
需要一个稳定的序号映射。**这个序号一旦发布就不能改**，否则老存档的塔头会变成别的型号。

    // ---- 以下三项【派生自 BlockState】，不写入 NBT（避免状态不一致） ----
    val kind:   TurretKind get() = (blockState.block as TurretHeadBlock).kind
    val tier:   Int        get() = blockState.getValue(TurretHeadBlock.TIER)
    val facing: Direction  get() = blockState.getValue(TurretHeadBlock.FACING)  // 指向底座

    // ---- 以下为需要存档的运行时状态 ----
    var health: Double = 0.0
    var shieldLayers: Int = 0
    var nextFireTick: Long = 0L          // 自调度：到点才开火（§4.12.2）
    var pendingXp: Int = 0               // 未满 7 点的经验
    var lastDamageTick: Long = 0L        // 护盾再生判定
    var kills: Int = 0

    /** 绑定的底座：由 §4.1.3 的双向幂等注册协议维护，**不写入 NBT** */
    @Transient var boundBase: TurretBaseBlockEntity? = null

### 5.8 协程使用红线

Kotlin for Forge 4.12.0 捆绑了 kotlinx-coroutines 1.10.2，但：

| 允许 | 禁止 |
|:---|:---|
| 非世界状态的异步计算（配置解析、资源加载、纯数学） | ❌ 用协程做「延时 N 秒后执行」的世界操作 |
| | ❌ 在协程里直接碰 `Level` / `BlockEntity` / `Entity` |
| | ❌ 用 `Dispatchers.Default` 后忘记切回主线程 |

**理由**：Minecraft 是单线程游戏循环。协程的 `delay` 不受服务器 tick 暂停、维度卸载、世界保存的影响，
会产生"服务器卡顿时协程照跑"的诡异 bug。

**「延时执行世界操作」一律用 §5.9 的 `TickScheduler`。**

### 5.9 TickScheduler：基于 tick 的延时队列

```kotlin
class TickScheduler {
    private val queue = java.util.PriorityQueue<ScheduledTask>(compareBy { it.dueTick })
    fun schedule(delayTicks: Int, action: () -> Unit) { … }
    fun tick(currentTick: Long) {
        while (queue.isNotEmpty() && queue.peek().dueTick <= currentTick) {
            queue.poll().action()
        }
    }
}
```

**用途**：殉爆连锁（每 0.5 秒炸一座）、榴弹延迟命中、核心放置时的分帧区块扫描。

**约束**：调度器必须挂在 **Level 或 BE** 上，并在对方失效时清空队列。
**绝不允许做成全局单例** —— 那会导致跨维度、跨存档的任务泄漏。

### 7.3 Kotlin 与 JS 的桥（`@KJSBindings`）

**全局对象名**：`TurretDefense`

```java
@KJSBindings(value = "TurretDefense", modId = "turretdefense", isClient = true)
public final class TurretDefenseBindings {
    private TurretDefenseBindings() {}

    /** 读取某个塔头面的显示数据；失败返回 null */
    public static List<String> getHeadInfo(int faceIndex) { }

    /** 请求升级某一面的塔头。返回 true 表示请求已发出 */
    public static boolean requestUpgrade(int faceIndex) { }

    /** 切换目标优先级。返回 true 表示已生效 */
    public static boolean setTargetPriority(int faceIndex, String priority) { }
}
```

**分工铁律（§2.8 复述）**：

| 层 | 只做 |
|:---|:---|
| **JS** | DOM 操作、标签页切换、按钮状态、把用户操作转成 `TurretDefense.xxx()` 调用 |
| **Kotlin** | 一切游戏逻辑、权限校验、数据读写、网络请求 |

**JS 绝不能直接改世界状态。** 升级/切换一律走 `TurretDefense.xxx()`，由 Kotlin 在服务端校验后执行。

**返回类型约束**：Rhino 能稳定转换的类型只有基本类型、`String`、`List`、`Map`。
**不要把 `BlockEntity` / `ItemStack` / `Entity` 直接传给 JS。**

- [ ] 缺少三个前置中的任意一个时，游戏给出**明确的缺失前置提示**，而不是崩溃
- [ ] 不装 JEI 时，模组功能完全正常（JEI 是软依赖）
- [ ] 模组 jar 体积 ≤ 5 MB

#### B. 方块与物品

- [ ] 三个方块均能正常放置、破坏、掉落自身
- [ ] 25 种塔头物品在创造模式物品栏里正确分组
- [ ] 塔头放置到底座 6 个面均能成功，**朝向正确**
- [ ] 塔头失去底座时**立即掉落**，世界中不存在孤立塔头
- [ ] 底座等级正确限制可装面数（T1 只能装 1 面，T5 能装 6 面）
- [ ] 底座**免疫爆炸、火焰、水、活塞**（用 TNT 与苦力怕实测）
- [ ] 塔头**可以被摧毁**（用 TNT 实测，确认生命值下降直至炸毁）
- [ ] 🔴 **爆炸不改地形**：在平地上引爆榴弹、自爆核心、终焉裁决、殉爆，
      结束后**地形与爆炸前逐方块完全一致**（§4.14.4）
- [ ] 🔴 **其他模组的爆炸不摧毁我们的方块**：用 TNT 炸底座与塔头，方块本体必须存活

#### C. 能量

- [ ] 核心燃烧燃料发电，能量缓存正确增减
- [ ] 外部 FE 输入可用（用另一个模组的线缆或测试工具验证）

- [ ] 能量分级表现正确（把能量调到 50% / 20% / 5% / 0% 逐一验证）

#### D. 索敌与开火

- [ ] 核心扫描产生快照，5 个塔头能同时攻击不同目标
- [ ] **塔头不自己做实体查询**（代码审查 + 性能探针确认）
- [ ] 炮塔有效射程 = min(塔头射程, 核心扫描半径)，**超出范围的目标不被攻击**
- [ ] 目标粘性生效：持续战斗中不会频繁切换目标
- [ ] 5 种炮塔的弹道表现符合设计（直线/抛物线/持续光束/连锁）

- [ ] 装错弹药被拒绝（过滤器生效）

#### E. 战利品

- [ ] 炮塔击杀生物后**不生成掉落物实体**，物品直接进底座缓存
